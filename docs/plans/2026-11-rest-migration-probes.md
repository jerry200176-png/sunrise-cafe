# Fail closed for legacy REST migration probes

## Evidence and decision

The production workflow invokes each phase's runners both for apply and for verification. The LINE Pay runner catches all REST failures and then replays both historical SQL files. The market-parity runner also applies when any probe is unknown; an HTTP 400 containing a column name is treated as absence. This can execute DDL on an already-ready schema after an outage or permissions failure. The LINE Pay SQL includes DROP, function replacement, UPDATE and REVOKE. Its plan entries remain unchanged and its historical SQL is not edited.

PostgREST documents `PGRST204`/`PGRST205` as *schema-cache* errors, not proof of a missing database object; `42501` is a permission failure and `PGRST000`–`003` are connectivity, initialization or pool failures. [PostgREST error reference](https://docs.postgrest.org/en/stable/references/errors.html), [schema cache](https://docs.postgrest.org/en/stable/references/schema_cache.html), [PostgREST MIT license](https://github.com/PostgREST/postgrest/blob/main/LICENSE). Flyway's [validate and repair APIs](https://github.com/flyway/flyway/blob/main/flyway-core/src/main/java/org/flywaydb/core/Flyway.java) separate validation from repair; [Apache-2.0](https://github.com/flyway/flyway/blob/main/LICENSE.md). Those are references for the decision, not imported code.

These two runners now only verify REST readiness. A successful probe requires HTTP 200 and a JSON array. Specific missing-object and cache codes produce a distinct diagnostic requiring catalog verification; all other statuses, malformed responses, absent credentials and network/timeout failures are unknown and stop the phase. Neither category applies SQL. No response body or credentials are logged. This deliberately suspends automatic first-time application by these two legacy runners: if a schema is genuinely missing, use a separately reviewed migration path after verifying database identity, ledger and catalog and satisfying all existing backup and authorization gates. A ready REST probe verifies only the selected fields, not the entirety of either migration.

## Both phases: current runner inventory and release blockers

This change fixes only the two named runners; a successful result does **not** clear the release hold.

- Postdeploy REST runners `ops-events`, `payment-request-sent`, `deposit-approved-notified`, `deposit-approved-claim`, and `deposit-approved-retry-key` can apply on absent, ambiguous, or insufficiently classified REST results. Some return success on missing credentials. `reservation-message-actions`, `reservation-message-batch`, and `line-guest-notification-deliveries` also treat broad 404/text matches as absence. Cache staleness is not established absence; these need separate fail-closed changes.
- `line-reminder-deliveries` likewise treats broad 404/text matches as missing, and its readiness check calls the **claim RPC via POST** with synthetic identifiers. That is a potentially mutating operation, not a read-only proof. Replace it in a separate reviewed change with a read-only catalog/signature check and appropriate tests; do not invoke the production RPC as a test.
- `line-guest-notification-deliveries` also runs three subsequent migrations based on absence in a REST-exposed version ledger; that result alone does not prove catalog state or that replay is safe.
- Predeploy `bank-transfer-reports` unconditionally issues two REVOKEs and two GRANTs when its ledger is already present, before ACL validation. Existing draft #507 independently changes that path to read-only verification and fails on drift; avoid a duplicate fix here. #507 must still resolve its grandfathered SQL gate and receive exact-head checks and independent review. Its ACL check does not prove privileges for every possible role.
- Predeploy `reservation-preorder`, `booking-meals`, `preorder-menu-seed`, `branch-guest-settings`, `branch-weekly-hours`, `reservations-deposit-transfer-info`, `branches-archive`, `line-deliveries`, `menu-option-sets`, and `no-show-advice`, and postdeploy `reservation-settlements`, use PostgreSQL ledger/catalog checks and apply on a missing version, subject to their existing per-runner gates; this inventory is not a proof that all catalog checks, concurrency handling, SQL or migrations are safe. `reservation-settlements` retains its existing founder-approval and backup constraints. The plan also lists manual-only SQL entries, which are not phase runners. The runtime bootstrap migration path is separate and not repaired here.

## Unresolved additive gate and safe integration

The existing additive gate deliberately rechecks the SQL mapped to a modified `apply-migration-*` runner. It reports ten findings in the unchanged LINE Pay SQL and will block this draft; #507 encounters the same class of blocker with its own unchanged SQL. This PR does not alter that gate, SQL, plan, approvals or labels. A possible separate design would verify exact SQL bytes against the trusted base and prove the changed execution path cannot run those bytes before treating an unchanged historical file differently. Any such change requires independent security review, adversarial tests for changing paths/SQL/plan/base and explicit compliance with F1; matching a hash alone does not establish that execution is safe. Until a compliant solution passes the existing governance process, this draft and #507 cannot be merged.

## Tests and limits

The node subprocess tests replace `fetch` with synthetic responses and supply only dummy credentials and a non-usable PostgreSQL URL. They cover success, missing credentials, 401/403/429/5xx, misleading error text, malformed/non-array responses, missing/cache codes, transport failure and a mixed ready/failing probe. They do not connect to production, use real customer data, or prove actual production schema readiness. Full CI, an independent review, unresolved runners, release gates and actual environment checks remain necessary.
