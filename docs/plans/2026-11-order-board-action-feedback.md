# 即時訂單看板動作回饋

## 問題與根因
店員點擊「開始備餐／完成出餐／已出餐」後，現有 action lock 已阻止同一頁重複請求，並在不確定結果時顯示核對提示，但卡片按鈕只變成 disabled，文字完全相同。使用者難以區分請求處理中和結果不明，不知道為何無法操作。此問題只影響提示，現有鎖與處理行為不變。

## 既有功能與範圍
搜尋 `lockedOrders`、`reviewState`、`updateStatus` 和 #493、#561。`src/app/admin/orders/page.tsx` 已保留每訂單 action lock 和結果未知的核對流程，沿用這兩個狀態；不得新增 API、通知或平行鎖。已完成的寫入由原有卡片狀態切換表示，查詢重整失敗仍顯示既有錯誤。多分店與不同訂單各自沿用既有資料結構，預點餐 link 不改動。

## 方案與驗收
使用按鈕既有 disabled 狀態，將送出中顯示「處理中…」、持有 review 狀態顯示「待核對」，並保留原操作名稱於可存取名稱；使用 `aria-busy` 區分正在處理。拒絕使用固定等待動畫假報成功。未送出與伺服器回應間不得顯示完成；網路失敗後顯示待核對，仍需沿用人工核對及解除流程；成功後顯示新狀態對應的動作。對未知結果不得自動重送。測試延遲、失敗、核對及成功；也涵蓋切換分店後舊請求晚到。

## 參考做法
- [WAI-ARIA Authoring Practices alert pattern](https://www.w3.org/WAI/ARIA/apg/patterns/alert/)：狀態訊息應可被輔助技術感知，但不能以動畫或顏色單獨傳達。延用現有 role=alert 的未知結果文字。
- [React `useState`](https://react.dev/reference/react/useState)（文件 CC BY 4.0）：由已有的 UI 狀態推導畫面，避免額外同步來源；不複製外部程式。
- 根因是兩種 lock 共用同一種不可操作的視覺文字；以現有 review 狀態區分處理中和待核對，並不承諾跨裝置或伺服器冪等。

## 上線與回復
只修改既有客戶端顯示，不變更 schema/API 或付款政策；發布需遵守現行部署暫停、CI 和獨立審核。回退為還原 UI commit。真實付款、實體出餐和跨裝置行為不在此變更的驗證範圍。
