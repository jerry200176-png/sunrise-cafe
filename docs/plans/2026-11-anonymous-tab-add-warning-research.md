# 加點結果提示：同分頁存續研究

## 目的與目前限制

#550 的元件內記憶體在面板卸載時消失；遮罩關閉或切換另一組可在請求尚未回覆時卸載畫面。結果未知的請求之後仍可能寫入，而重開後沒有提示。#550 本身仍是局部緩解，不提供持久冪等、跨裝置安全或晚到請求防護。

## 不存客戶識別的候選

每次加點的 POST **之前**，先同步把本分頁的「隨機操作代號及狀態」寫進 sessionStorage 並讀回核對；沒有姓名、電話、房號、訂位 ID、品項、金額或其他訂單內容。這仍是操作次數與狀態的行為中繼資料，不應稱作完整隱私隔離。純研究模組使用結構嚴格、最多 64 筆、版本化的匿名紀錄；逾時或卸載不刪除未解決項。系統能確定自己的單次請求在寫入前被拒絕時，只可移除該次代號，不得清除先前其他未知項。成功表示已提交，但單次 GET 成功不證明特定加點已顯示；研究模組只允許明確核對後清除已提交項，未決／未知不能由其他操作清除。

這是全分頁的保守提醒：由於刻意不保存任何訂位識別，重新開啟面板或重整後無法指出哪一筆；其他訂位亦會顯示「本分頁先前有加點結果尚未確認，請核對所有可能相關訂單」並在重新送出前提示。這可能造成保守誤報，是不儲存識別資訊的代價，不可把它寫成已偵測同一張訂單的重複請求。

若 storage 讀取／存入／讀回失敗、資料格式錯誤或達容量上限，研究模組回報不可用，不默默丟棄警示；研究分支已接入兩個 UI：提示不會辨識個別訂位，儲存失敗時明示離開或重整後提示會消失，需店員確認才繼續。送 POST 前會檢查結果；`window.sessionStorage` 屬性本身也可能拋錯，SSR／隱私模式不能假定可用。單純存一個已知結果 flag 且在回應後才寫，無法保護「送出後立即關閉」的空窗。

## 測試與界線

以假的 sessionStorage 及 jsdom 合成重建 store，檢查送出前 pending、卸載重建、未知／已提交／拒絕的分離、兩次操作互不清除、資料不含任何客戶識別、storage 拒絕與錯誤資料處理、容量上限以及獨立 storage 不共享。僅證明合成模型，不證明瀏覽器在當機／儲存清除／權限異常時可靠持久化，涵蓋兩個實際 UI 的 jsdom 卸載重建與拒絕送出；未驗證真實瀏覽器、PostgREST 或資料庫。

不同分頁、裝置、瀏覽器或關閉工作階段後通常不共享；分頁複製／opener 可能複製初始 storage 而產生保守誤報。使用者、瀏覽器或同來源其他程式可清除／更改資料，XSS 可存取同來源 storage；不可依賴它授權操作或作為交易帳本。未知请求即使稍後 GET 看不到仍可能晚到，查一次不能安全清除。真正的跨端重複寫入保護仍由 #441／#502 的 server-side durable idempotency 和狀態競態治理追蹤。

正常提交後也須人工核對並確認，才清除該分頁的已提交提示；這對日常操作增加負擔，需產品評估。未知或尚在執行中的項目不提供手動清除，可能一直留到分頁工作階段結束。隨機代號避免 storage 被清除後，舊請求晚回覆誤修改新操作；無法補救已被清除的警示。

## 參考做法

- [MDN `sessionStorage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)：同來源、同分頁 session，重整後通常保留；新分頁複製與 session 終止有不同邊界。
- [MDN `Storage.setItem`](https://developer.mozilla.org/en-US/docs/Web/API/Storage/setItem)：儲存可能因額度等原因失敗，不能把嘗試寫入當成成功。
- [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)：可安全重送需要服務端支援；本研究只顯示提醒，不重用其實作或宣稱已有伺服器冪等。
