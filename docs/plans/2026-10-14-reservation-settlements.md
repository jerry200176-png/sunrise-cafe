## 這份 SQL 做什麼（白話）

| # | 改動 | 為什麼 |
|---|------|--------|
| 1 | 新表 `reservation_extensions`：每次延長／提早離開記一列，當下的每小時房價一起存下來 | 之後房價改了，舊的延長費不會跟著變；報表也看得到延長了多少 |
| 2 | 新表 `reservation_settlements`：每組客人最多一筆結帳紀錄（包廂費、延長費、餐費、扣掉的訂金、折扣、實收、付款方式、誰結的） | 現在結帳只在點餐單記「已收」，收了多少、怎麼收的都沒留 |
| 3 | 函式 `extend_reservation_stay`：改結束時間＋記延長紀錄，一次完成 | 兩台同時延長不會互相蓋掉 |
| 4 | 函式 `settle_reservation_checkout`：重算金額、核對店員看到的數字、寫結帳紀錄、記已收、轉「已完成」，全部一次完成 | 兩台同時結帳，後到的那台一定失敗；結帳和取消／延長不會交錯 |
| 5 | 防重疊規則改成「取消」和「沒來」都不佔時段 | 店員標了沒來之後，上一組就能延長 |

不改、不刪任何既有資料列；新表只有伺服器（service_role）能讀寫。

## 計費規則

- **原訂時段**：照訂位當時的 `total_price`（不受之後房價調整影響）。
- **延長／提早離開**：只有多出或少掉的分鐘數 × 當時的每小時房價（平日／假日依台北日期）。
- **訂金**：訂位總價的一半（無條件進位），和現在的訂金規則一樣；延長不影響訂金。
- **應收** = 包廂費 + 餐費 − 已付訂金 − 折扣。訂金比應付還多 → 記為「要退多少」。

## 需要你決定的 4 件事（都已照「推薦」寫進 SQL）

1. **提早離開要不要少收？** 推薦：要（跟現在畫面上的算法一致）。所以訂金付了一半、客人坐不到一半就走，系統會算出要退錢。
2. **實收一定等於應收嗎？** 推薦：是。要少收就走「折扣」，並填原因；多收（小費、找零）先不記。
3. **付款方式有哪些？** 推薦：現金、刷卡、LINE Pay、轉帳、其他。
4. **誰能打折？** 推薦：只有老闆（owner）和店長（branch_manager），而且一定要填原因（照 Q3、Q4）。用 `ADMIN_PASSWORD` 登入的帳號在系統裡算老闆。

## 已驗證（本機 PostgreSQL 16，模擬正式環境的表）

| 情境 | 結果 |
|------|------|
| 延長 30 分（平日 300/hr） | 記一筆 +150 |
| 用舊的結束時間再延長一次 | 擋下（`stale_end_time`） |
| 延長撞到下一組 | 擋下（防重疊規則） |
| 下一組標「沒來」後再延長 | 成功 |
| 延長後才調房價 | 結帳仍用延長當時的費率 |
| 店員看到的金額已過期 | 擋下（`amount_changed`） |
| 一般店員打折／店長打折不填原因 | 擋下 |
| 店長折 50 並填原因 | 600＋延長 300＋餐 250－訂金 300＝850，折 50 → 實收 800；訂位轉已完成、餐點記已收 |
| 同一組結第二次 | 擋下（`already_settled`） |
| 兩台同時結帳（一台現金、一台刷卡） | 只有一筆，後到的失敗 |
| 結帳進行中另一台延長 | 等結帳完成後失敗（客人已離場） |
| 2 小時訂位、坐 30 分就走、訂金 300 | 應收 0、要退 150，必須填退款方式 |
| 已取消的組補收餐費 200 | 只收餐費，狀態維持取消 |
| 台北週六凌晨 1 點（UTC 還是週五） | 用假日價 |
| 還沒到的組結帳 | 擋下 |
| 未登入（anon）呼叫 | 沒有權限 |
| 同一份 SQL 跑兩次 | 不會出錯 |
| 檔尾的回滾 SQL | 能完整還原 |
