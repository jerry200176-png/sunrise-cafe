# 使用者建立失敗的確認流程

## 問題與既有功能
管理者建立帳號時，POST 或回應內容可能失敗、逾時或中斷；伺服器可能已建立帳號。原頁面沒有錯誤處理，也沒有連點鎖，容易誤以為未建立而重送。搜尋 `createUser`、`/api/admin/users`、`fetchWithTimeout`、帳號清單和未合併 PR，既有入口只有使用者管理頁；沿用現有讀取逾時工具與清單，不改帳號 API、角色或身分政策。

## 方案與驗收
送出前在 sessionStorage 留不含個資的待確認旗標，並同步鎖住按鈕；POST 與 JSON 讀取均有界、絕不自動重送。確定的用戶輸入或權限錯誤顯示原因；無法確認結果時提示先重新整理清單，並保留鎖定直到管理者明確核對後選擇解除，重新整理頁面也不會解除。清單讀取失敗不得解除鎖定；已提交但後續稽核或回應失敗仍視為未知。密碼不放進持久儲存，結果未知時清除密碼。無法確認先前請求是否已在伺服器結束，人工核對也不能保證稍後不會完成，畫面須說明。關閉分頁／換裝置可能失去旗標；完整解法須服務端冪等機制，非本次變更。

送出期間與結果未確認時鎖住帳號、顯示名稱、角色與分店欄位，畫面以僅存在記憶體的原申請摘要協助核對；送出時清除表單密碼，摘要不含密碼。重新整理後不還原申請內容，明確提醒依原申請查核。重新載入收到 401/403 或身分已無使用者管理權時清除先前的管理表單與清單。

使用隔離 mock 測試成功、4xx、網路失敗、非 JSON、標頭及回應內容逾時、連點和核對後的行為；不連線正式資料、不建立真實帳號。回退僅還原 UI 改動，不影響資料庫。觀察方式為後台錯誤回饋及相關測試，無新增個資事件。

清單只有帳號與分店關聯都查詢成功、筆數完整時才能供核對；分店關聯查詢失敗不再當成空分店。若資料數量超過 PostgREST 單次回傳上限，清單會顯示錯誤而非誤判完整，需另行實作安全分頁。每次重新讀取都撤銷先前核對資格，舊回應不可覆蓋最新結果；非 owner 未關聯分店會明確標示。帳號列與分店關聯仍是兩次查詢，並非同一交易快照；送出端的建立帳號、關聯與稽核也仍非原子操作。

## 參考做法
- [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)：不確定結果的寫入需要同一 idempotency key 才能安全重試；目前帳號 API 沒有此契約，因此不自動重送。
- [SWR error handling](https://swr.vercel.app/docs/error-handling)（MIT）：區分讀取失敗和重新讀取；沿用專案現有工具，不引入新套件或自動重送寫入。
- 根因是寫入結果與網路回應不是同一件事；僅顯示通用失敗或只鎖按鈕不能解決回應遺失後重複建立。
