# 後台訂單列表分頁（#434）

## 根因與範圍
目前訂單 API 一次讀取完整分店資料，資料服務上限會靜默截斷；看板與列印站都以完整陣列判斷訂單，漏單可能影響出餐。沿用現有分店授權、PostgREST 及超時工具，不引入 schema、權限或付款政策變更。

## 參考做法
- Stripe [pagination](https://docs.stripe.com/api/pagination) 以 cursor 繼續讀取，避免以會隨新增刪除位移的 offset 接續。
- Supabase [SQL to JavaScript API](https://supabase.com/docs/guides/api/sql-to-api) 示範多欄排序、limit 及 OR/AND；PostgREST 為 MIT 開源授權。既有 `reservation-list-query.ts` 亦採時間加 UUID keyset；不複製外部程式。
- 根因是沒有可延續的穩定排序而非畫面顯示筆數；以 created_at + id 排序、明確處理 nullable created_at，保持各頁次序確定。

## 設計
新呼叫端顯式帶 limit，得到 `{items,nextCursor}`；游標驗證時間和 UUID 並綁定分店及篩選，保留時間微秒。舊呼叫端仍收到陣列，但伺服器分頁讀取，遇錯或達安全上限時明確失敗，不回傳假完整資料。看板只查進行中狀態；列印掃描以共用八小時規則的固定起點、未列印及進行中狀態篩選，仍逐頁讀取，空明細留待下次掃描。待確認的訂單依本機識別碼經分店授權逐筆讀取列印狀態，不受歷史總量影響；找不到或查詢失敗保持鎖定。途中錯誤保留舊畫面及既有列印鎖定。限制遍歷上限並顯示錯誤，避免無限迴圈與靜默漏單。

分頁是多次讀取，不是資料庫快照：期間新增／刪除或狀態變化不能保證跨頁一致；即時看板繼續定時重新讀取。測試權限、同時間 UUID 排序、null、游標驗證、跨頁讀取及失敗不當成功。未碰正式資料，真實 PostgREST 上限與效能待部署後確認。

同分店分頁掃描維持單一進行中作業；定時、即時與手動刷新在掃描中合併為一次後續重讀，避免長於刷新週期的掃描永遠被取消。切換分店立即作廢舊結果並可啟動新查詢；測試涵蓋多頁延遲、連續刷新與跨分店遲到回覆。

訂單狀態修改成功後推進本頁操作版本並安排重讀；在成功之前開始的掃描不可覆蓋已確認的狀態。後續讀取未完成或失敗時保留該結果並顯示刷新失敗；這不提供跨裝置版本控制或伺服器冪等保證。

每筆訂單的操作以同步 ref 單飛；跨分店工作階段的遲到結果不直接套用，必須重新核對成功才解除鎖定。逾時或非成功回應保守視為結果未知，刷新確認後仍需人工核對及確認延遲完成風險才解除，絕不自動重送。鎖及待確認狀態僅存在目前頁面記憶體，重新整理、其他分頁或裝置不受保護，且仍需伺服器端 CAS／冪等才能處理跨裝置競態。

成功回覆必須在期限內讀取並解析為 `{ok:true}`；即使 HTTP 為 200，HTML、截斷 JSON、錯誤格式或停滯內文皆屬結果未知，保持鎖定並以訂單 ID 核對。

核對須使用已授權的分店和訂單 ID 取得並展示實際狀態（包含已出餐、取消）；進行中清單缺少該筆不代表已核對。每次請求刷新先撤銷舊的核對結果，失敗、404 或被更新刷新取代的回覆不解除鎖定；清單與指定 ID 狀態不一致時，以後者修正或移除該卡片。
