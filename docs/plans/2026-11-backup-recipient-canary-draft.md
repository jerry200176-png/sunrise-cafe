# `BACKUP_AGE_RECIPIENT` synthetic canary workflow draft

Status: review draft only. The existing release/SQL hold remains active; this draft does not clear it. Runnable YAML is stored outside `.github/workflows` at [`docs/workflow-drafts/backup-recipient-canary.yml`](../workflow-drafts/backup-recipient-canary.yml); GitHub Actions will not discover it there. It has not been copied into the active workflow directory, dispatched, or merged.

## Evidence and scope

The user reports that the GitHub Repository secrets UI lists the name `BACKUP_AGE_RECIPIENT`. No secret value was read. Presence of the name does not establish the value is a valid age recipient, that any particular workflow can access it, or that a held private key can decrypt ciphertext encrypted to it.

The current #466 draft uses a `workflow_dispatch` `age_recipient` input. That is separate from the repository secret; the canary draft consumes only `${{ secrets.BACKUP_AGE_RECIPIENT }}` and does not change or invoke #466's input workflow.

The canary encrypts only a fixed, non-sensitive synthetic string. It does not access a database, call `pg_dump`, use production backup artifacts, inspect or emit the recipient, or handle a private key. It tests two bounded facts: the job can access the configured repository secret, and a private-key holder can decrypt that particular artifact. It does not prove source identity, actual backup quality, retention beyond this one-day artifact, or complete Supabase recovery.

## Workflow and secret authorization

- Trigger: manual `workflow_dispatch`; a first, secret-free guard job fails unless the ref is exactly `refs/heads/main`. The secret-bearing canary job depends on that guard, so non-main dispatches fail the workflow rather than being reported as a successful skipped job. No inputs are accepted.
- Job scope: protected GitHub Environment named `backup-recipient-canary`; no checkout; `permissions: {}`; five-minute timeout; serialized runs; pinned `actions/upload-artifact` v4.6.2; one-day artifact retention.
- Required external GitHub configuration before activation: repository/environment administrator must create the named environment, restrict its deployment branches to `main`, and configure required reviewers. Confirm repository Actions permissions and artifact audience. Do not move the file into `.github/workflows` until those controls are verified. The YAML in this draft cannot itself prove that the environment protection exists.
- Secret scope: the only secret referenced is the repository secret `BACKUP_AGE_RECIPIENT`, passed to the encrypt step's process environment. No user input can override it. That step forces `BASH_ENV=/dev/null` and empty `SHELLOPTS`, then starts with `set +x`; no reliance is placed on GitHub's secret masking. It rejects CR/LF, whitespace, extra lines, and anything other than one canonical 62-character age X25519 recipient before writing a mode-600 recipients file; age then validates the recipient checksum during encryption. It captures age diagnostics outside the artifact and emits fixed failure messages. The temp directory is removed on exit.
- Trust boundary: GitHub Environment approval protects only jobs that reference that environment. It does not prevent another repository workflow from referencing the repository-level `BACKUP_AGE_RECIPIENT` secret. The named environment's existence and policy are unverified. If workflow-wide technical isolation is required, the secret must be moved to an environment-scoped secret; otherwise repository workflow write access, branch protection, and all workflows that can reference repository secrets must be reviewed. This draft does not change secret scope or claim the environment blocks every workflow.
- Artifacts contain only the age ciphertext, SHA-256 checksum, and a minimal manifest with synthetic scope and ciphertext digest. The workflow reports only artifact ID and upload digest. The canary artifact is visible under normal repository Actions artifact access; ciphertext is synthetic and does not include customer data.
- Recipient format is deliberately limited to one native age X25519 public recipient (`age1...`). SSH recipients (which can expose a key fingerprint in the ciphertext header) and age plugin recipient formats are rejected. The manifest contains no recipient text or fingerprint; the ciphertext is not claimed to reveal no protocol metadata. Review the artifact audience before any activation.

## Holder-side verification and failure controls

After an authorized canary run, the private-key holder downloads the artifact using their own GitHub access, verifies `sha256sum -c canary.txt.age.sha256` from the downloaded artifact directory, decrypts `canary.txt.age` locally with their own key (for example, `age --decrypt --identity <local-private-key-path> --output canary.txt canary.txt.age`), and compares the result with the fixed three-line synthetic string in the workflow. Because the workflow rejects any whitespace or additional recipient line and accepts one canonical age X25519 recipient, successful decryption verifies the tested key matches that sole accepted recipient. It does not verify the repository secret's value directly or any other artifact. They report only run/artifact ID, checksum pass/fail, decrypt pass/fail, and whether the plaintext comparison passed. They do not send the key, recipient, decrypted file, or raw diagnostics.

Missing/unavailable secret, age installation failure, malformed/multiple recipient, encryption failure, empty ciphertext, any missing/empty required artifact file, artifact upload failure, missing artifact ID/digest, or failed checksum/decryption/plaintext comparison is a failed canary. Each artifact file is checked individually before upload; `if-no-files-found: error` remains an additional guard. Tool stderr is not emitted. A failed canary does not trigger a backup, migration, retry against production, or private-key recovery action. Any correction to the repository secret value is an external credential/configuration change and is out of this draft's scope.

- PyYAML parsed the draft and static checks confirmed manual-only trigger, fail-on-non-main guard dependency, empty token permissions, the exact repo-secret context, `BASH_ENV`/`SHELLOPTS` overrides, ciphertext/checksum/manifest-only upload paths, per-file nonempty checks, and one-day retention.
- Synthetic tests use age v1.2.1 and disposable keys only. The one-recipient encryption/checksum/decrypt/plaintext path passed; the relative checksum verified after moving the artifact to a different directory; the matching key decrypted and the second key did not. The old unconstrained two-recipient file decrypted with both synthetic keys; the draft rejected the same two-key value before encryption. A synthetic SSH recipient was also rejected. Blank lines, CR/LF, empty, malformed and multiline values failed without ciphertext or candidate values in captured stdout/stderr. Each required artifact file was also removed in turn and the draft's extracted pre-upload check failed closed.
- The GitHub artifact action, environment approval settings, repository-secret access, and GitHub-hosted execution were not exercised. A malicious `BASH_ENV`/`SHELLOPTS=xtrace` inherited environment was simulated with step-level overrides; the marker and synthetic recipient were not emitted. The synthetic keypairs and temporary plaintext were local test material only; no existing private key or repository secret was accessed.

## 參考做法

- GitHub Actions — [Using secrets in GitHub Actions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions): pass secrets only through the required step context; do not print them. Adapted by limiting secret exposure to the encryption step and keeping diagnostics fixed.
- GitHub Actions — [Managing environments for deployment](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments): environment protection applies to jobs that reference that environment; it does not globally scope a repository secret. Branch restrictions and reviewers must be configured outside this YAML.
- age — [age encryption](https://github.com/FiloSottile/age) (BSD 3-Clause): public-key encryption uses recipient-only encryption and holder-side identity decryption. Reimplemented as a fixed synthetic canary; no age code is copied.
- Root cause vs symptom: the previous evidence established only that the secret's name appears in UI, not that its value is runtime-usable or matches a held key. A ciphertext-only canary tests that narrow compatibility chain; it deliberately does not claim recovery-point validity.
